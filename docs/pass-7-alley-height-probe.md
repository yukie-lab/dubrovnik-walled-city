# 第7パス(2)— 「北の家並みに 1 層足す」を、決める前に測る

第6パスの終わりに三人の批評家が別々に到達した結論 —
**「空のリボンを実在の 7〜11° に近づけるには、北の家並みに 1 層足す以外に道がない。
それは第3パスの屋根の海と第4パスの視線を動かすので、このパスの権限では決められない」**
に対し、ユーザーの指示は **「まず実測してから決める」**。

**まず試作を当てて数字を出し、ユーザーの判断を仰いだ。結果は A の採用**(下の「採用」節)。

## この計測から言えること

批評家の前提のうち**半分は当たっていて、半分は外れていた**。

- 当たり: 1 層足せばリボンは動く(18.1° → 15.8°)。ただし **7〜11° には届かない**。
- 外れ: 「第4パスの視線を動かす」— **A は動かさない**。海も島も山も画素単位で不動。
  視線を動かすのは B(キャップ)だけで、その B はリボンを 0.1° しか改善しない。

7〜11° に入れるには、残る道は**設計幅 2.18 → 1.9m**(画家の案)か **2 層**。
どちらも通行判定と `life` の配置に触れるので、別の判断になる。

## 正直に書いておく副作用 — `life` の乱数列がずれる

`plan.js` を触ると、階が増えたぶん窓や縦樋の数が変わり、**`life` の生成器が

| | 現状 → A |
|---|---|
| `v8_luza` の `stradun`(磨石の見えている面積) | 28.7 → **24.3%** |
| `v8_luza` の `life` | 3.0 → **7.1%** |

| `v1_stradun_t2noon` の `stradun` | 6.0 → **7.9%** |

記録しておく。定点の画素差が `v1_stradun_t4dusk` で 62% に達するのはこれが理由で、
要素の割合(空・海・屋根・山・島)はそのどれも動いていない。

# 計器の故障 — 分類マスクがアルファ抜きを無視していた

調和の門を通す途中で、**`harmony.mjs` の分類マスクが葉と松を「四角い板」として
数えていた**ことが分かった。`v2_alley` で `veg` が 4.8% → 19.9% と跳ね、
`_whatis.mjs`(別の計器)は同じ画で 1% 未満と答えていた。

原因: マスクは `MeshBasicMaterial({ transparent: false })` で描き直しており、
**`alphaTest` も `map` も引き継いでいなかった**。実測(`tools/_alphacut.mjs`、新規):

```
surround.pine    alphaTest=0.42  map=RGBA
life.foliage     alphaTest=0.45  map=RGBA   ← 葉のカードが四角いまま描かれる
life.lampPool / house.grimeBand / window.reveal / sky.clouds / monument.fountain*
                 transparent=true           ← 石を覆うのではなく染めている物
```

直した物(`harmony.mjs` / `stonestat.mjs` / `_whatis.mjs`):

1. **`alphaTest` で抜く物は抜く。** ただし `map` をそのまま付けると RGB が掛かって
   **分類色(や id)そのものが壊れる**ので、`map_fragment` を差し替えて
   **アルファだけ**を採る。
2. **半透明の飾りはマスクに描かない。** 灯だまりも煤の帯も窓の内法も雲も、
   その画素の「持ち主」ではない — 持ち主は後ろの不透明な物。

直した後の同じ画: **`veg` 19.9% → 3.2%、`stone` 72.1% → 88.5%。**

**この誤りは第4パス以降の harmony の値すべてに乗っている。** 向きは常に同じで、
**植生を多く数え、その後ろにある物(石・海・空・山)を少なく数える**。
影響が大きいのは葉が近くにある画(路地)で、`v5_sea` の `veg` 0.4% のように
遠景では 0.0〜0.2pt しか動かない。第4パスの「糸杉/水」も再測の対象。
**本パスの採点は直した計器で取り直した値だけを使っている。**
