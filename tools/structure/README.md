# 構造アサーション一式

目は、この種の欠陥にとって悪い測定器です。3cm の浮きは 10m 先では見えず、1m 先では
明白で、正しく座った壁が影のせいで間違って見えることもあります。幾何は正確に知れる。
なら幾何に訊けばいい。

これはビジュアル回帰でも、スクリーンショット比較でも、リンタでもありません。
**シーンの実際の幾何に問い合わせて、この街の何かが浮いているか・沈んでいるか・
隙間があるか・塞がっているか・自分自身と食い違っているかを、決定的に、数秒で答えます。**

```
node tools/structure.mjs                      # 全部の検査
node tools/structure.mjs --only grounding     # 検査を選ぶ
node tools/structure.mjs --seed 12345         # 別のシードの街
node tools/structure.mjs --map shots/g.svg    # 接地誤差の俯瞰図
node tools/structure.mjs --json out.json      # 機械可読の出力先
```

違反が 1 件でもあれば終了コードは **1**。ビルドの門にできます。

---

## 前提 — 生成をレンダリングから切り離す

`src/world.js` が街の唯一の組み立て定義です。`main.js` もこの一式も、そこを通ります。
組み立てに WebGL も canvas も DOM も要りません(three のオブジェクトは CPU 側の
データ構造です)。`tex.js` だけが canvas を要りますが、テクスチャの画素は幾何に一切
影響しないので、`domshim.mjs` が薄い影武者を置いて **実物のコードをそのまま** 走らせます。

* **この一式は本物の生成器を検査します。** 建物がどこに建つかを自分で計算して、
  その計算を自分で検算するようなことはしません。地形の高さ関数も街路網も、
  実行時の世界と同じ一つの出所から来ます。
* シードは `src/seed.js` が一元管理します。各モジュールは「塩」だけを持ち、
  実際の種は `rngFor(salt)` が世界のシードと混ぜて作ります。
* **決定性を最初に確かめます。** 同じシードで街を二度組み、全ての transform と
  フットプリントの構造ハッシュを比べます。違えば、その下の全ての主張は無意味なので
  終了コード 2 で即座に止まります。

## 索引

三角形は 110 万本あります。総当たりは禁止です。`geom.mjs` の `Grid` が XZ の一様格子に
三角形を入れ、レイと点の問い合わせを定数時間に近づけます。全 14 検査で **7〜8 秒**。
「重いから今日は走らせない」が起きた瞬間、この一式は無価値になります。

## 検査

| 検査 | 何を主張するか |
|---|---|
| `terrainAgreement` | 地形「関数」と描かれた地形「面」が一致する(構造的に一致させ、許容差で吸収しない) |
| `grounding` | 置いた物の底が、その下の支持面に載っている(浮きと沈みを符号で区別) |
| `footprintCorner` | 建物の四隅が斜面から浮いていない(中心だけの検査は必ず見落とす) |
| `stairs` | 蹴上が範囲内、踏面に隙間が無い、同じ run の中央値から外れた段が無い |
| `walkability` | 踏み抜け・登れない段差・横の閊えが無い。描かれた床と体が立つ床が一致する。**城壁の周回が閉じている** |
| `envelope` | 門の通路・塔の内部から、上へレイが 1 本も漏れない(屋根と壁の取り合いの穴) |
| `colliderAgreement` | 見えない壁(衝突はあるが石が無い)と透ける壁(石はあるが衝突が無い) |
| `interpenetration` | 立体どうしが 5cm を超えて重なっていない(意図した接合は札で宣言) |
| `coplanar` | 同一平面で 4mm 未満しか離れていない面の対(Z ファイティングの巣) |
| `crossRepresentation` | 歩く網・建てた石・地図が同じ街を指す(辺の下に舗装があるか、網が連結か) |
| `manifold` | 立体は閉じている。全ての稜線がちょうど 2 面に共有され、巻きが揃い、体積が正 |
| `backface` | 片面材で組んだ中空の殻になっていない(内部から見て面が裏を向いていない) |
| `thickness` | 石と宣言した物に厚みがある。両面材で立体を装っていない |
| `plate` | 面の裏 6cm が立体の内側にある(= 板を貼っただけではない) |
| `seating` | 上に載せた石(狭間石など)が本当に載っている。段が石の下を横切っていない |

## 部位の札 — 「城壁が壊れている」では直せない

`wall.curtain` は三角 1.4 万枚の 1 メッシュです。「境界稜線 3,108 本」と言われても、
人間はどこを直せばいいか判りません。生成側が三角形の範囲に**作り方の名前**を付けます:

```js
const PARTS = [];
const part = (name) => { …I.length/3 を記録… };   // walls.js
geo.userData.parts = PARTS;                        // body / parapet / kerb / tower / …
```

`manifold` と `plate` はこの札を見て、部位ごとに測って報告します:

```
wall.curtain:slitNiche  境界稜線 668 本 / 三角 1670
wall.curtain:tower      3 面以上が共有する稜線 466 本
wall.curtain:body       正逆の数が釣り合わない稜線 6 本 / 三角 3380
```

`node tools/partmap.mjs <名前> <shots.txt の 1 行>` は同じ札を色で塗って撮ります。
「あの茶色い板は何か」を推測ではなく色で答えるための計器です
(入れ子の作り手は抜けるときに呼び出し元の札へ戻すこと — 戻し忘れると、
階段の巨大な板が `pier` の名前で報告されます。実際にそうなりました)。

## 意味の札は生成側が宣言する

検査は「これは何か」を推測してはいけません。`tagMesh(mesh, 'wall.curtain', { solid: true,
masonry: true, groundContact: true })` のように、作った側が宣言します。

`thin`(布・葉・水面)は**宣言であって、報告を黙らせるための免除ではありません**。
理由を `reason` に書きます。書けないなら、それは薄い面ではなく手抜きです。

## 許容差は物理から決める

`tolerances.mjs` の全ての定数に、物理的な根拠を書いてあります。

**合格させるために許容差を緩めるのは失敗状態です。** 意図した接合の一覧に物を足して
報告を黙らせるのも同じです。検査が間違っているなら検査の論理を直して理由を書く。
世界が間違っているなら世界を直す。

例(`FLOAT_MAX = 0.010`): 歩行距離で人間が段差として気づく最小は約 5mm。地面は 3.2m
格子の三角形で近似しているので、1cm 浮くと接地影に隙間が出る。

## ラチェット — この一式は増えるだけ

* 今後、目で見つけた欠陥は、**直すと同時にここへ恒久的な主張として書く**まで
  「直った」と見なしません。
* 一度緑になった検査が黙って消えることはありません。
* **一つの物を座らせるために個別のオフセットを足すのは禁止です。** 接地は唯一の
  地形関数から導出されます。ある一件を黙らせて兄弟が壊れたままになる修正は失敗状態です。
* 違反を見つけたら、**修正を書く前に根本原因を述べます**。

### この規律が実際に効いた例

`house.plinth` が 313 枚浮いていた件で、最初に見えた「直し方」は巾木の y に定数を
足すことでした。根本原因を先に述べる規則があったので、そうはなりませんでした:

> `facesOnStreet` は街路に面さない面に `groundY: null` を返し、`buildings.js` が
> `h.yBase + 0.5` という定数で代用していた。

さらにその奥に、もっと大きな原因がありました:

> 地形メッシュは地形関数を 3.2m 格子で標本化して線形補間する。だから関数の値と
> 見えている面は平均 0.10m(最悪 8m)食い違う。関数を見て物を置くと、その差だけずれる。

直し方は `plan.surfaceAt(x, z)` — メッシュと同じ格子・同じ三角形分割で「描かれている
地面」を返す関数を一つ作り、地形メッシュ側もその格子を使うようにしました。一致は
許容差ではなく構造で保証されます(実測: 15,401 標本で最大差 0.000m)。
`terrainAgreement` がその一致を恒久的に見張ります。

### 城壁の全面的な作り直し(板 76% → 6%)

「板が貼ってあるだけ」「貼る板が別の場所にある」「床が板で浮いている」。
目で見えた 3 つの訴えは、測ると 1 つの原因に集まりました:

> **面を一枚ずつ張っていた。** 巻きの向き・端の小口・段差の隙間を人間が全部
> 覚えていなければならず、忘れた所が必ず板になる。実測: 垂直面の 40.8% が
> 中心線を向き、境界稜線 3,108 本、零面積の三角 1,541 枚。

直し方は個別のパッチではなく作り方の変更です。**閉じた断面を経路に沿って掃く**:

| 部位 | 前 | 後 |
|---|---|---|
| 壁体 | 区間ごとに外面・内面・デッキ・軒裏を別々に張り、門でだけ塞ぐ | 周回全体を 8 頂点の閉じた断面で 1 本に掃く。切れるのは門だけ |
| 塔 | `ring()` = 外周の曲面 1 枚(中空の衝立) | `drum()` = 厚みを持つ環状の立体。外面・内面・天地の環・門口の小口 |
| 囲い階段 | 側壁 2 枚 + 天井 + 屋根 4 枚(境界稜線が三角の 88%) | П 断面の掃引 + 段の下の閉じた台 |
| 胸壁・内縁 | 段の帯ごとに閉じた箱を積む(隣が同じ面を二重に持つ) | ラン単位で 1 本の掃引。小口は両端だけ |

掃引で保証されること: 外向きは断面の巻き(反時計回りの辺 (du,dy) に対して
(dy,−du))から出る。小口は端にしか無い。段差は**幅 4cm の蹴上**として掃かれる
(幅 0 で二重化すると閉じようのない切れ目が段の数だけ開く — 実測 115 個)。

その結果 `side: THREE.DoubleSide` を落とせました。**両面材は欠陥を隠す道具で
あって、厚みを作る道具ではありません。** 落とした瞬間に、囲い階段の小口が
通路を塞いでいた(星形でない断面を頂点 0 から扇にしていた)ことが見えました。

### 目で見つけて、恒久的な主張になった欠陥

* 掃引の蹴上で `(b−a)×(d−a)` が零ベクトルになり `normalize()` が (0,0,0) を返す
  → 真っ黒な面。→ 二つの三角の外積を面積のまま足す(面積加重法線)。
* 段の格子(`YQ`)を `round(t·segN)/segN` で作っていたが、`segN=1` は段ではなく
  斜路。`plan.wallWalkYAt` は直線補間なので、歩廊の石と足の高さが半段ずれた
  (`geomtest --scan` が 238 点で `FLOOR_LOW`)。→ 両者を同じ式にした。
* 塔の門口の迫(アーチ)を高さを確かめずに立てていた。テラス高さで歩廊が入る
  聖ヨハネでは、アーチが王冠より 2.8m 高くせり上がり、空に角が二本出た。
  → 迫を組むのはデッキの上に 2.6m 以上の石があるときだけ。
* 王冠を胴と一緒に切っていたので、門口の上が空まで抜け、テラスの床裏が
  「宙に浮いた濃い板」として空に貼りついた。→ 持ち送りと胸壁を別々に切る。
* 市側の胸壁が 0.95m しかなかった(25m の歩廊で腰の高さ)。→ 1.12m。
* **狭間石(メルロン)が「塀の上で飛び出している」** — 目で見えた指摘。測ると
  244 本中 89 本の底が石に載っていなかった。原因は三つ、どれも同じ形をしている:
  「石の寸法を、載る相手の寸法と無関係に決めていた」。
  - 段のある区間(蹴上 0.19m / 帯 1.0m)で、幅 1.09m の石が必ず帯の境をまたぐ。
    片端が 0.20m 埋まり片端が 0.17m 浮く。→ 石は**一つの帯の中**に収め、
    幅も帯の長さに合わせる。段の境は狭間(石と石の間)に落ちる。
  - 奥行き 0.72m を胸壁の厚み(0.70m)と無関係に固定していた。→ 胸壁の厚み −6cm。
  - 塔の王冠では帯 0.55m に 0.72m の石。しかも王冠は 26 角形なので、面の
    真ん中の半径は crownR·cos(π/26) しかない。→ 帯を 0.80m に広げ、
    石は多角形の内接半径に合わせる。
  - 斜路の区間では天端も傾いている。水平な箱は片端が 7cm 浮く。→ 石ごと傾ける。
  `seating` 検査がこれを恒久的に見張る(`userData.seatOn` で載る相手を宣言)。

### 目で見つけて、恒久的な主張になった欠陥(その 2)

* **記念建築が宙に浮く** — `monuments.js` の `synth()` は足元を「中心 1 点」で
  決めていた。28×8m の量塊が斜面に建つと、中心が地面に触れていても隅は
  1.9m 浮く(実測 (-138,-18) で 1.92m、(-128,-8) で 1.09m)。plan.js の家生成器と
  同じ規則 ―― 足元を外へ 0.6m まで格子で見て最も低い所まで降ろす ―― に統一。
  最悪 0.91m → 0.29m、`grounding` 274 → 224 件。
* **塔の門口が凱旋門になっていた** — 半幅 1.75m・迫元 deckY+2.0m は開口
  3.5×3.75m。しかも (a) 袖壁の半径を `t.r`〜`t.r*1.03` の 3% 殻にしていたので
  胴から 0.26m せり出した「浮いた板」に見え、(b) `drum()` の門口は 26 角形の
  面の中点判定で落ちるので、`g.a±g.w` で作った袖壁と最大 1.1m ずれて隙間から
  空が見え、(c) 迫の裏(通路の天井)が巻き任せで上を向き、`geomtest` に
  「足の上 1.2m に床」と出て FrontSide では真っ黒に抜けていた。
  → 開口 2.7m・迫元は胸より上(deckY+1.75)、半径は drum の実面、門口の縁は
  実際に落ちた面の境目(`gapEdges`)、迫の裏は明示的な外向き。
* **空に縦の継ぎ目** — 大気の筆むらを `atan(d.x, d.z)` で貼っていた。方位 180° で
  値が 2π 飛ぶので、空にまっすぐな線が一本入る(夜ほど目立つ)。方位を円周に
  写すと継ぎ目は消えるが天頂から放射状の縞が出る。**方向ベクトルを 3 次元の
  noise に渡す**のが唯一の正解(継ぎ目も特異点も原理的に存在しない)。

### 塔の頂は「眺めるための場所」— `tools/_tview.mjs`

ミンチェタに登っても海が見えない、という指摘を測った。テラスの床(y=34.75)に
立って全方位へレイを撃つと、**外が見えるのは 21.0%** だった。原因は胸壁の天端が
床上 1.30m(目線 1.62m の下なので本来は見えるはず)+ その上に 1.02m の狭間石が
周長の半分を塞いでいたこと。天端を床上 0.95m、狭間石を 0.73m・間隔 1.82→2.45m に
して **42.3%**(ミンチェタ)/ 41.6%(北東隅)/ 51.4%(聖ヨハネ)。

### 見え方も測る — `tools/_view.mjs`

「上から海が見たいのに景色が見えない」は感想ではなく数で言える。歩廊の目の
高さ(+1.62m)から外向きに扇状(水平 ±30°・俯角 12°〜仰角 6°)へレイを撃ち、
石に当たらず抜けた割合を測る。狭間石を 1.20m→1.02m・間隔 1.82m→2.15m にして
`land` 35.0% → 43.2%、`gatePloce` 35.5% → 48.1%、全体 58.6% → 62.3%。

### 目で見つけて、恒久的な主張になった欠陥(その 3)

* **植木鉢の下が左右で尖る** — 内張りを「半径 0.29 のまっすぐな円筒」で作って
  いた。胴は上 0.32 → 下 0.24 に絞れているので、胴の半径が 0.29 を下回る
  y=0.26 より下では内張りが胴を突き抜けて外に出る。八角形の角が一番遠くまで
  出るので、左右に尖りが立つ。→ 内張りは土から縁までの短い錐台にして、
  胴の絞りの内側に収めた。
* **石段に座る人の脚が石に埋まる** — 足を「座面の 0.55m 下」に着く姿勢にして
  いたが、実測ではその位置の床は 0.30m 下しかなく、**40 人全員**の脛が
  0.15〜0.26m 舗装に沈んで「足の無い人」になっていた。→ 膝を高く、足を
  座面 −0.30m へ。さらに足の着く場所に床が無い段では座らせない。40 → 1。
* **記念建築の巾木が舗装より 0.16m 低い** — 面が街路の縁からわずかに外れると
  `f.paved` が false になり、巾木が地形の高さに置かれる。0.40m の巾木のうち
  0.15m しか出ず、躯体の足元が切れて「家が浮いている」と読める(スタート
  地点の左の家)。→ 記念建築の面では「歩ける面が地形より舗装の厚みぶん
  高いなら、そこは舗装」と見なす。接地違反 224 → 217 件。

* **ピレ橋が「地面に置いた空き箱」に見える** — 橋そのものは三連アーチで
  組んであった。埋めていたのは**地面のほう**で、空堀の底を 1.95m にして
  いたため桁下(2.72m)まで 0.8m しかなく、迫元 0.57m のアーチが丸ごと土に
  埋まっていた。上から見ると欄干 2 枚と床だけが残り、箱に見える。
  → 堀の底を 0.20m まで掘り下げた(海面より上・乾いた壕は維持)。
  併せて欄干を厚み 0.18m の閉じた石(笠石つき)にした。1 枚の面だと天端が
  刃になり、上から見て「壁を 2 枚立てた空き箱」に見える。
  **「板に見える」の原因が、板ではなく地形の側にあることがある。**
* **ピレ橋の「板を貼り合わせた空箱」** — 橋脚を側面 4 枚だけで立てていた。
  天も地も無い、文字どおり板を貼り合わせた空箱。西端の橋脚(-177.6)は
  デッキ(-176 まで)より 2.4m 外に出ていたので、上が開いたまま空を向き、
  上から覗くと箱の中が見えた。→ 天と地を張って閉じた石にし、デッキを
  -178.4 まで伸ばして橋台の上を渡す。空堀も「橋が渡っている範囲」だけに
  絞り、縁は海の棚ではなく取り付きのテラスと同じ陸の高さへ戻す
  (棚へ戻すと橋の西に 10m の断崖ができる)。

* **塔の門口の「アーチっぽいところが板」** — 門口の迫を、内外二枚の壁面
  (rI・rO)と、その間を一枚で渡した迫の裏(soffit)だけで作っていた。
  厚みはあるのに **開口の縁が厚みゼロの切り口** なので、塔の中から見上げると
  壁の縁が刃になり、迫の裏だけが「宙に張った帆」に見える。奥行き 2.6m を
  一枚で渡していたため継ぎ目も無く、樽天井ではなく曲げた紙だった。
  → (1) 迫の裏を奥行き方向に 5 帯へ割り、通路の中ほどを暗く落とす。
  (2) 面から 0.13m せり出した **迫石の輪(アーキヴォルト)** を内外両面に巻く。
  輪の内法は開口より 0.10m 広く取る — 歩ける帯(半幅 1.4m)を 1mm も削らない。
  輪は開口を狭めるものではなく、縁を包むもの。
  (3) 袖の返しも迫の裏と同じ帯数に割る(1 対 5 で当たると T 字の継ぎ目 = 穴)。
  **「板に見える」の多くは面の枚数ではなく、縁が切り口のままであること。**
* **ミンチェタの中の「浮いた板」** — ギャラリー床の円盤の内側の境界を、
  歩廊の縁 `deckEdgeAt` を 26 分割の弦でなぞって作っていた。
  (a) 弦の矢が最大 7cm あり、その隙間から円盤の下が見えた。→ 104 分割。
  (b) 円盤は水平なのに、歩廊は塔の中を斜路で登る。低い側では円盤の縁が床から
  0.8m 浮き、下腹(y−0.50)が丸見えになる。**水平な床と斜路を突き合わせると、
  必ずどちらかの縁が浮く。** → 内縁の下端を station ごとに真下の歩廊まで
  下ろして擁壁として閉じ、外周(rG)側は水平のまま保つ(下腹は線織面になる)。
  (c) 円盤は歩廊より 3cm 低く置く。上に出すと縁が段差(見た目の刃)になる。

### 植生 — 1 個の形を回して並べない(`src/trees.js`)

屋根の次に、来たことのある人が必ず見るのが木。ダルマチアの署名は
**アレッポ松の平頂の傘 + 糸杉の縦線 + 剥き出しの白い石灰岩**。
以前は 3 個の手作り形状(球の傘・円錐・塊)を 1,370 本にスケールと回転で
流用していた。**同じ輪郭の反復は、島ごと既製品に見せる。**

作り直した原則 —

* **成長から作る。** 幹は傾きねじれ、枝は上の 1/3 にだけほぼ水平に出る。
  葉は枝の**実際の先端**に置くので、樹冠の形が枝の構造から出る。個体ごとに
  座標から乱数列を作るので、1,461 株すべて輪郭が違う。
* **インスタンスではなく空間の塊に焼く。** 全部違う形なのでインスタンスに
  できない。150〜170m の格子で 12 メッシュにまとめ、頂点属性 `aSway`(根元 0 →
  枝先 1)と `aPhase` で個体ごとに違う位相で揺らす。描画呼び出しは 3 → 12、
  三角形 318,824。全 30 定点で最大 172 call / 最低 56fps。
* **葉の板は樹冠の面に寝かせる。** `tilt` の意味を取り違えて板を立てたら、
  平頂の傘が縦のブロッコリーになった。**カメラを向く板は幹が見える距離で必ず破綻する。**
* **針葉の房はアルファのテクスチャ。** 矩形の板のままだと「厚紙の破片」。
  逆光で空が透けるレースの輪郭は、この抜けが作る。
  幹と葉を 1 枚のテクスチャで賄うため、左隅に不透明の正方形を焼いて幹の UV を
  そこへ向ける(材質を分けると描画呼び出しが倍になる)。
  **`CanvasTexture` は `flipY`。UV(0,0) はキャンバスの下。** 上に置いたら
  幹が丸ごと透明になった。
* **線形空間の色は sRGB の感覚より 2 段明るい。** 葉に 0.25/0.40/0.30 を
  与えたら、島が霜に見えた。0.052/0.098/0.068 まで落として初めて松になる。
  さらに、水平に寝た葉は空の環境光をまともに受けて青白くなる —
  葉だけ間接光を 0.38 倍に落とす。
* **配置は生態。** 密度は勾配・斜面の向き(北は日陰で濃い)・谷筋(凹)・
  標高(樹林限界)・汀からの距離で決まる。一様なランダム散布は
  「木を置いた」であって「森」ではない。
* **スルジは森ではない。** 乾いたマキと剥き出しの石灰岩。緑の森にしたら
  地理的に誤り。壁際(踏み固められた glacis)は岩、斜面を登るほどマキが
  matrix になるよう、地形の色を標高で振る。

### ロヴリイェナツを島から陸続きに戻す

「高い所から海を眺めたい」に応えて要塞へ行けるようにしようとしたら、

### 海を深くする — 動かしていたつもりの数字が、毎フレーム消されていた

「沖をもっと深い青に、浅場はそのまま」という依頼。消散係数 σ の赤と緑を
上げれば水柱長に比例して効く…はずだった。**σ を 2.4 倍にしても、画素の
0.47%・最大差 5/255 しか変わらなかった。**

原因は `sea.update()` が `uInscat` を毎フレーム **ハードコードの
(0.055, 0.20, 0.42) で上書き** していたこと。作成時の値も、こちらで
書いた値も、1 フレームで消える。**以前 AAA の回で「散乱を 2.8 倍にした」と
報告した変更も、実際には一度も効いていなかった。**(あのとき改善したのは
海底の明度と砕波のクランプで、散乱ではない。)
→ 生成時に値を置く uniform は、update が触るなら **そこが唯一の真実**。

**物理としての正しい直し方。** 深い水の色は Beer–Lambert の漸近値
σ_s/σ_t で決まる。だから **散乱源 σ_s を固定したまま消散 σ_t だけ上げる**:
  浅場 scat ≈ (σ_s/σ_t)·σ_t·column = σ_s·column  — **σ に依らない**
  深場 scat → σ_s/σ_t                            — σ が大きいほど青い
`update()` の色度を SCAT/σ から作るようにして、σ が実際に効くようにした
(実測 画素の 15%・平均 R−0.61 G−0.67 B+0.32)。色を足すのとは別物。

**測って分かった、本当の制約。**
* **ドロップオフは制約ではない。** 深さを 2 倍(最深 39m → 78m)にしても、
  沖の水の **平均色は動かない**(ΔR 0.05 / ΔG 0.06 / ΔB 0.09)。
  見えている距離では水柱がとうに長く、海底は既に何も返していない。
* **制約はフレネル。** 16m の胸壁から見下ろす角度(8°)では反射率が 0.4〜0.9。
  沖の水の色は **大半が空の反射** で、水そのものの色は少数派。だから σ を
  極端に上げても沖は 5.7/765 しか動かない。水面・フレネルは触らない約束
  なので、ここが上限になる。
* **σ は浅場のほうに 12 倍強く効く。** 沖 |Δ|5.7 に対し浅場 |Δ|22.2。
  掠め角の沖は反射が支配し、見下ろす浅場は水の色が全部だから。
  「浅場は変えずに沖だけ」は、この物理では成立しない。

**σ を選ぶのは目。** `?sigR=&sigG=&dropoff=` と
`__sea.set({r,g}) / __sea.reset() / __sea.before() / __sea.dropoff(v)` を出し、
三枚(現状・中程度・強め)を見比べてもらって **強め (1.00, 0.16, 0.030)** で確定。
出荷値は `SIG_DEFAULT`。基準の組 `SIG0/INS0` は散乱源を決めるためのもので、
出荷値とは別に置く — 一緒にすると σ を変えた瞬間に散乱源まで動いて、
「消散だけ上げる」が成立しなくなる。
実測: 沖の彩度 0.170 → 0.172(反射が支配するので動かない)、
浅場 0.320 → 0.375、沖合の波 0.407 → 0.456。

**ヘッドレスの計器を全部落とした。** `typeof window !== 'undefined'` で
判定して `location` を読んだ。domshim には window はあるが location は無い。
**使う物そのものを確かめる。**

### 表題 — 「画面」をやめて「最初の一瞬」にする

背景を絵や動画ではなく **動いている街そのもの** にした。早朝 7.1 時
(太陽 高度 12°・方位 82° ＝ ストラドゥンの通り芯)を等速 0.18 m/s で
西へ漂う。入城は切り替えではなく **降下** — 型が溶け、カメラはそのまま
2.6 秒で下りてピレ側に立つ。`started` を渡すのは補間 k=1 の瞬間だけで、
そこで表題のカメラとプレイヤーの姿勢は **ビット一致** している。だから
継ぎ目が出ない(実測 Δx 0.000 / Δz 0.000 / Δyaw 0.0000)。

**UI も実機で測る。** `tools/titletest.mjs` を常設。ここで計器の作り方を
3 回間違えたので書いておく。

* **「1 標本の移動量」で継ぎ目を測ってはいけない。** 標本の間隔がブラウザの
  都合で 40〜180ms に揺れるので、長いフレーム 1 枚が 9.5m の「跳び」に見える。
  速度は **瞬間移動の検出**(桁が変わる)にだけ使い、滑らかさは
  **単調性**(降下のあいだ下りと寄りが一度も引き返さない)で見る。
* **閾値は設計値から引く。** 漂いの閾値を 0.25m にしていたが、設計値は
  0.229m だった — **設計どおりに動いていても落ちる**閾値で、通っていたのは
  読み込みの揺れのおかげ。数字が合わないときは、まず「どちらが正しいか」を
  設計から決める。ここでは漂いが遅すぎるのが実態だったので速度を上げた。
* **音の札は実態を映す。** ブラウザは操作前の発音を許さないので、表題の
  第一フレームでは文脈は suspended で待っている。ところが「最初の操作で
  音を立ち上げる」共通処理が札のクリックでも先に走り、札の分岐が
  「既に鳴っている」を見て **最初の一押しが消音になっていた**。
  札からの操作は共通処理から除外し、最初の一押しは「鳴らす」にした。

**表題に計器を出さない。** 時刻の弧もデバッグ読み出しも `body.titling` で
伏せ、降下と一緒に現れる。扉はひとつ、という約束は画面の隅まで及ぶ。
おまかせ歩きは表題から外して街の中(Shift+1〜4)へ移した。

### 時刻の弧がポインタに付いてこない — 写像が 2 つあった

右上の時計をドラッグしても印がポインタから離れる、という報告。実測すると
**最大 76px(キャンバス幅 296 の 1/4)** ずれていた。原因は 4 つ重なっていた。

* **ドラッグは x に比例、描画は弧の角度**。印の x は `cx − cos(π·tt)·R` で
  余弦分布。ポインタは等速で動くのに印は端で止まり中央で走る。
* **半径が高さで頭打ち**。`R = min(w·0.36, h−8−PAD)` は 106.6 と 74 の小さい方で
  74。つまり印は **全幅の 50% しか動けない**。
* **日没の先でクランプ**。`tt` を ±0.08 で切っていたので 20:50 以降は完全に静止。
* イベントは `#timeCtl`(168px)、座標は `#timeArc`(148px)から取っていた。

直し方は **写像を 1 つにする**こと。x は時刻に比例(= ポインタにぴたり付く)、
弧は **高さだけ** を与える。`timeToU / uToTime / uToX / xToU` を ui.js から
export し、描画もドラッグもこれだけを使う。弧は円弧をやめ、同じ式で引いた
日周の曲線にした(印が道から外れないため)。夜の側は地平線の下に点線を引き、
そこもドラッグできることを示す。

**UI は実機で測る。** `tools/arctest.mjs` を常設 — 実際にブラウザを開き、
Start を押し、ポインタロックを外してドラッグし、
(1) ポインタ x → 設定された時刻、(2) その時刻 → 描かれた太陽の x
の両方を実ピクセルで確かめる。**片方だけ正しくても印はポインタから外れる。**
実測 写像 0.1〜0.7 分 / 描画 0.3〜0.5px。

**手で送る道と自動で進む道の範囲を別々に持っていた。**
自動 4.7〜23.6 / キー 4.9〜21.9 / ドラッグ 5.60〜20.74 の三重。
夜を伸ばしたとき自動だけ直したので「9 時から 5 時まで飛ぶ」ように見えた。
**同じ量の上限は 1 箇所にしか書かない。**

### 階段の最上段が床とチラついた — 計器は最初から鳴っていた

見晴らしの砲座で「階段の手前の床に板のような物がチラつく」と報告。
正体は **石段の最上段の天板(17.400)と砲座の天端(17.400)が同一平面** で、
見る角度で交互に勝つ Z ファイティング。

原因は `addRun` が段を `s = 0..n` の **両端込み** で出すこと。つまり
**走りの両端の段は、着く床とぴったり同じ高さになる**。段は「床へ上がる
ための石」であって床そのものではない。両端の段だけ 12mm 沈めた。
ついでに、折れ線の節で前の区間の s=n と次の区間の s=0 が二重に出ていた
(`interpenetration` 3881 → 3512)。

**この欠陥は `structure` の `coplanar` が最初から鳴らしていた**
(`5 × wall.curtain|steps 最悪 @176.814, 17.4, 59.477`)。dim 段の出力を
「情報」として読み飛ばしていた。**dim は「無視してよい」ではなく
「まだ絵にどう出るか判っていない」の意味。** 絵で出たら、その行を探す。

**間引きは「重複」を確かめてから。** 節の二重段を無条件に 1 枚消したら、
ミンチェタの螺旋の井筒に 5.87m の穴が空いた(`geomtest` FLOOR_LOW)。
螺旋では 2 枚は向きが違い、**2 枚合わせて曲がりを埋めている**。
向きの差が 20° 未満のときだけ捨てる。

### ロヴリイェナツの上半分が 5.65m 宙に浮いていた — 誰も鳴らなかった理由

ユーザーの指摘で発覚。`mk(r0, r1, h, yc, tint)` の **第 4 引数は中心の y**
(CylinderGeometry は原点中心)なのに、下段の蛇腹の天端 32.85 を「積み始め」
だと思って `33.2` と書いた。主塔は 26.7〜39.7 に置かれ、蛇腹(45.35)との間に
**5.65m の空隙**。胸壁・蛇腹・メルロン環・旗竿が丸ごと宙に浮いた。

**なぜどの計器も鳴らなかったか。** `structure` の `seating` は **物と物** の
据わりしか見ない。要塞は 1 メッシュに融合してあるので、その中の空隙は原理的に
映らない。`geomtest` / `trapstest` / `piercetest` は歩ける所しか見ない。
**塊の中を測る計器が無かった。** → `tools/masstest.mjs` を常設。

**問いの立て方で 3 回外した。記録しておく。**

1. 鉛直線の切れ目を数える → 中が空洞の塔(ミンチェタの螺旋・鐘楼・教会の身廊)
   が全部鳴った。**建物は中が空いているのが普通。**
2. 正しい問いは「**その高さに石が一片でもあるか**」。水平に八方から撃つ。
   ただし半径を決め打ちにすると隣の建物を拾う(スポンザ d12.9 は鐘楼、
   イエズス会 d9.0 は民家)。→ その建物自身の footprint から半径を取る。
3. 遠くから撃つと隣が先に当たり、`castRay` は最初の 1 つしか返さないので
   「範囲外だから無し」と誤判定した(スポンザが 10.5m 空白と出た)。
   → **自分の足元のすぐ外(r + 1.2)から撃つ。**
4. 柱・噴水のような「積んでいない単体」は対象外にする。物と物の据わりは
   `seating` の担当。

**計器は「鳴らないこと」ではなく「鳴るべき時に鳴ること」で検証する。**
主塔の y を誤値に戻すと 5.5m で鳴り、直すと ALL CLEAN になることを確認した。

ついでに出たもの: **メルロン環の位相が面と 30° ずれていた。**
`ROT + e·120° + 60°` という当て推量で辺の中点を出していた。three の
CylinderGeometry は頂点 k を局所 (sin θ, cos θ), θ = k·2π/3 に置くので、
辺の中点は θ = (k+0.5)·2π/3 を rotateY(ROT) で回したもの。**ライブラリの
規則から出す。当て推量の位相は必ずどこかでずれる。**
そして 1 辺に置ける数も辺の長さ(R·sin60°)から決める — 決め打ちにすると
角からはみ出して宙に浮く(実測 上の環で ±10.4m 対 辺の半長 9.0m)。

### 南の街区を迷路にしたら、隠れていた前提が 5 つ折れた

「北は 1667 年後の定規で引いた櫛、南は焼け残った中世の不整形」— この対比を
出すために、南の路地を **狭く・不規則な間隔で・途中で振れる折れ線** にした。
その途端、2 点の直線を暗黙に前提していた場所が次々に壊れた。記録しておく。

* **`streetY` が路地を「両端の x が同じか」で判定していた。** 曲がった路地が
  東西街路と誤判定され、床が z=1.5 の高さ(2.6m)に張り付く。地形は 7.1m
  なので、家の帯の隙間に 4.5m の落とし穴ができた(`trapstest` が 3 箇所)。
  **種類は kind が持っている。座標から推測しない。**
* **`alleySamples` / `groundAt` / 庭塀の補完が `pts[0]`〜`pts[1]` しか見ていなかった。**
  折れ線対応にした(`nearestOnPolyline` の弧長 `s` で解く)。
* **路地の床は幅方向に水平でなければならない。** 直そうとして
  `terrainHeight(x, z)` にしたら、横断勾配で床が傾き、両側の巾木が舗装に
  対して上下にずれた(`grounding` +72)。中心線の高さを使う。
* **路地が城壁に突き当たった。** 行き止まりの長さを乱数で振ったので、初めて
  壁に届く路地が出た。舗装が壁体に潜り、足の解決が歩廊(14.6m)へ跳んで
  「床が 5m 食い違う」と鳴った。壁から 6.5m 手前で切る。
* **振れ幅には上限がある。** 家の帯は路地の x から作られるので、路地だけ
  振れると家を食い破る。実測で **±0.65m まで**(±0.8m で `piercetest` 3 件)。

**「見た目のために据わりを壊さない」の 2 例目**(1 例目は狭間石の幅)。
どちらも「実測で上限を探して、そこで止める」で決着した。

**計器が間違っていた例:** 見晴らしの砲座へ上がる螺旋(`stjohnTop`)を、
walktest は歩廊との距離で測って「行き止まり」と鳴らしていた。この階段が
着くのは歩廊ではなく砲座の天端。**測る相手が違う。** 砲座と比べる分岐を足した
(実測 d=1.84 / 許容 3.80 ✅)。テストを緩めたのではなく、問いを直した。

**汚れ帯の位置を半厚から出してはいけない。** 城壁の足元にデカールを貼ろうと
して `wallNodeHalf` を面の位置として使ったら、裾勾配(scarp)のぶん外面が
0.7m 外にあり、帯が壁から離れて通路に浮いた(歩行網スキャンが IN_SOLID 5 件)。
半厚は **デッキの厚み** であって足元の面ではない。内面だけに貼り、外面
(アーセナルの脚)は surround.js 側で頂点色の勾配として持たせた。

### AAA 批評ループ 第 N 回 — 4 観点の指摘から出た「一般則」

批評家 4 体(光と露出 / 建築 / マテリアル / 生活)を並列で入れ、全員に
「実際に shots/*.png を開く・imgstat で数値を取る・原因を file:line に紐づける・
定数値まで書く・ファイルは編集しない」を課した。返ってきた 32 件のうち、
**同じ形の間違いが観点をまたいで繰り返されていた**。

* **「高さ」で性質を決めていた。** 海底の色は y<0.4、汀の濡れ帯も泡も塩の線も
  海面からの高さだけ。だから海と繋がっていない低い床(空壕 0.3m / glacis 0.5m)

* **同じ材質の色度を、頂点色が三方向に脱色していた。** メルロン 5.5% / 床 3.4%
  暖色 / 壁面 無彩色。掛ける相手が同じ石でも、頂点色の彩度が違えば結果が割れる。
  → **頂点色は明度の器に徹する。色度を決めてよいのはテクスチャと material.color
  の 2 か所だけ**(潮間帯だけが唯一の例外)。
* **時刻に追随しない定数。** 天空光の輝度は 07:24〜19:30 でほぼ一定なのに直射は
  12.9 → 0.06。日向:日陰が 8.9:1 → 1.3:1 に潰れ、夕方が全部「曇天」になっていた。
  露出も同じで、同じ舗石が朝 sRGB 231・夕 121。**比が 1.3:1 になった時点で、
  それは太陽のある晴天ではない。**
* **到達不能な分岐。** パラソルを畳むコードは書いてあるのに、時計が 22.1 で
  朝へ飛ぶので一度も描かれなかった。`cafeOn` の `h < 24.0` も同じ。
  **書いたのに走らない分岐は、書いていないのと同じ。**
* **部位の札が嘘をついていた。** パラソルが `life.pigeon`、井戸の蓋が `life.lamp`。
  札で検査する仕組みがここで壊れる。計器を信じる前に札を数えること。

**幅を広げたら据わりが壊れた例(記録):** 狭間石を 1.06m → 1.45m にすると
「柵」から「切り欠きのある壁」に変わって正しく見えるが、段のある胸壁で石が
蹴上を跨ぎ、底の隅が最大 0.14m 浮く(`seating` 0 → 27 件)。底を埋めると
今度は「埋没」で 186 件。実測は 1.20→5 / 1.24→15 / 1.28→25 / 1.45→27。
**見た目のために据わりを壊さない。** 1.20m(石:隙間 1.40:1)で確定した。

**却下した指摘:** 接地影に GTAO を足す案。`main.js:214` に「実測で 2.3% の画素
しか変えず、描画コール +71 / fps −13」と既に記録があった。**測って捨てた判断を、
測らずに戻さない。** 代わりに `skyvis.js` のバウンス下限 0.30 → 0.16 だけ直した。

### 橋の袂まで来られるのに、橋に上がれない

ロヴリイェナツの岩から海沿いに下りて橋の西の袂に立てるのに、いつまでも
橋へ上がれない、という報告。原因は **四つ**、すべて「西は行き止まりだった
頃の名残り」だった。西を陸続きにした変更が、それを一度に露出させた。

* **collide に「西へ行かせない壁」が残っていた。** `x = Math.max(x, x0+0.4)`。
  橋の袂に立つと 2.2m 東へ弾かれる。橋から落ちない仕掛けは横(壕)だけでよい。
* **地形に 0.5m の溝があった。** 取り付きのテラスは x=−179 で終わり、壕の枝は
  x>−179.5 から始まる。その隙間はどちらの枝にも入らず、素の岩棚の式へ落ちて
  深さ −1.6m。海側から誰も歩いて来なかったので、誰にも見えていなかった。
* **歩ける帯がデッキより 2.4m 短かった。** 「描かれているが乗れない床」。
* **帯の西端を描かれたデッキの端とぴったり揃えていた。** その一点を踏むと
  帯から外れて壕(0.5m)へ落ちる。しかも `groundAt` は層を **今の高さ** で
  解くので、一度落ちると以降ずっと壕の層を拾い、二度と橋に戻れない。
  → **落ちる縁では当たり判定を描画より広く取る。** 逆向きの誤差は必ず穴になる。

そして、直した拍子に出てきたもの:

* 壕の肩を `|x+170|` の **対称式** で書いていた。西の肩(橋台の下)を直すと
  東の肩(城壁の足元)まで動き、第三アーチが地面に埋まった。左右の肩は
  同じ場所には無い。
* **門の敷居の舗装帯**が門から外へ ±6.5m の固定長・固定幅。ピレでは橋の
  欄干より外へはみ出し、壕の上に宙に浮いた板が 4m 突き出していた。
  帯が壁体へせり上がるのを止めるための下限クランプが、実地面がはるか下に
  あるときは逆に板を空中で支えていた。支えのある station だけ残す。

### 乾いた壕が川に見えていた — 「高さ」で海を決めていた

上の壕を歩けるようにしたら、壕が水を張ったように見えた。三つ重なっていた。

* 海底の色を **高さ 0.4m 未満** で塗っていた。壕の底は 0.3m。
* 汀の濡れ帯・泡も **海面からの高さ** だけ。壕の底(0.3m)も glacis(0.5m)も
  「渚」だった。
* 潮上帯の白い塩の線が壕の底(0.4〜0.9m)を **水平に一本** 横切っていた。
  これが「水面」に見えた正体。

**高さは「海かどうか」を決めない。** 近景地形の格子で、外周の海から
低地を塗り広げて到達判定を作り(`seaConn`)、頂点属性 `aDry` で渡した。
海面メッシュも同じ性質の欠陥を持っていた — 沖の波頭と陸側の頂点を結ぶ
三角形が地面を突き抜ける。海底図の A チャンネル(誰も読んでいなかった
「陸か否か」の旗)を **陸の高さ** に変え、陸の上の水面を沈めた。

`walktest` に「城壁の外を回る(岩 ⇄ 橋 ⇄ 門)」6 区間を常設。
`trapstest` は「入れるのに帰れない」しか見ない — 「近くまで来られるのに
上がれない」は誰も見ていなかった。

### 塔の天端で「斜めに浮いた板」— 式が三つに分かれていた

砲座から歩廊へ降りた所で、床の板が斜めに浮いて見えると報告があった。正体は
**塔の天板(厚み 0.6m)の縁**で、原因は二つ重なっていた。

* **塔の天端は水平な砲床なのに、歩廊が斜路のままその上を横切っていた。**
  聖イヴァンで歩廊 14.22m に対し天板 14.65m。天板の縁が歩廊から斜めに
  突き出す。→ `wallWalkYAt` に「天端が歩廊を兼ねる塔の中では歩廊を天端の
  高さへ寄せる」を入れた(斜路は塔の外で終わらせる)。
* **天板の切り欠きを「角度」で切っていた。** 半径の小さい所で歩廊の帯より
  広く切れ、帯の脇に天板の小口が露出する。歩廊が天端と同じ高さになった今、
  切り欠きは要らない(胸壁と持ち送りだけ切ればよい)。

そして本題 — **歩廊の高さの式が三箇所に書き写されていた。**
`plan.wallWalkYAt`(足)/ `walls.js` の `YQ`(胸壁・内縁・メルロン)/
掃引の station 列(デッキ本体)。plan 側だけ直したら描画が取り残され、
`geomtest` が「床 y14.25 / 足 y14.60」と鳴った。
コード自身が「描画と足が必ず同じ格子を使うための唯一の関数」と書いてある
のに、実際には三つあった。`plan.wallWalkYOn(i, t)` を唯一の入口にして
三箇所とも差し替えた。**式を書き写した時点で、いつか片方だけ直す。**

斜路の区間は端点 2 つしか station を持っていなかったので、塔の近くでは
2m 刻みに細かく刻む(高さがもう直線ではないため)。

ついでに防波堤(ポルポレラ・カセ突堤)も「天板と側面 2 枚」で、端も底も
無かった。上から見ると水面に浮いた板。閉じた塊にした。
`culltest` 実測 0.000%、`walkability` 332 → 317。

### 見晴らしの砲座(カヴァリエ)を足したときに壊したもの

「手前を塞ぐ物を 0% にしたい」に応えて、聖イヴァン要塞の上に一段高い天端を
載せた。**最初に要塞の中心へ置いたら、城壁の周回が切れた** —
`route:walls` が 15 点で食い込み、歩廊の有効幅が 9 点で 0.00m になった。
**要塞の天端は歩廊そのもの**で、そこに塊を置けば道を塞ぐ。海側へ外し、
半径 5.4m → 2.6m に縮めて解決(歩廊の中心線から 3.2m 逃がす)。

**縁は胸壁ではなく膝より低い縁石。** 立てた瞬間に 0% は消える。
仰角 −8° の射線は 0.26m の縁石には当たらない(実測)。

計器の限界も出た —
* **床が二層ある所は (x,z) だけの既訪では拾えない。** 要塞の天端 14.6m を先に
  塗ると、その上の砲座 17.4m へ二度と来られない。種は高い方を優先する。
  `trapstest` も同じ限界を持つ(上層は「帰れない場所」の検査から漏れる)。
* **歩き方の刻みが粗いと階段が登れないと誤判定する。** 1m 刻みで歩くと 1 段を
  跨ぎ、`collide` の「段の中に立っている者は外へ出す」規則に弾かれる。
  0.25m 刻みで歩けば通る。ゲームは毎フレーム 0.1m ずつ動く。

実測: **(178, 57) 高さ 17.4m — 海率 25.0% / 手前 0%**。
行ける 1,785 点のうち、手前が 0% になるのはここだけ。

### 眺めのよい場所 — `tools/viewtest.mjs`

「高い所から海が見たい」に主観で答えないための計器。行ける場所を洗い出し、
目の高さから方位 36 × 仰角 4 = 144 本の射線を撃って、**最初に当たったのが
海だった割合**と、**22m 以内の石に当たった割合(視界のすぐ前を塞ぐ物)**を数える。

    node tools/viewtest.mjs [--minY 12] [--step 2.5] [--top 12]

* **`accept` で海を弾くと海率が全点 0 になる。** 射線は海にも当たらなければ
  ならない。当てる対象に海を含め、当たった物の名前で分類する。
* **種は門の内側だけでは足りない。** 格子の一歩(2〜3m)は階段の踏面より粗く、
  城壁の歩廊まで登れないまま終わる(高さ 12m 以上が 681 点しか出ず、歩廊が

実測(2026-08-22): 海がいちばん見えるのは **南東の聖イヴァン角 (178, 58)

**ミンチェタの天板は高さ 34.7m でも海率 10.4%・手前 37%** —

### 入れるのに帰れない場所 — `tools/trapstest.mjs`

街を格子に切り、ゲームと同じ規則(`plan.collide` + `plan.groundAt` + 登れる段差)
で **有向グラフ** を作る。落ちるのは一方通行なので、行ける先から戻れるとは
限らない。出発点から到達できて出発点へ戻れない格子 = 閉じ込められる場所。

    node tools/trapstest.mjs [--step 1.25] [--all]

塊ごとに「入口」— 帰れる場所から罠へ渡る辺 — も出す。そこに欄干を立てるか、
その一歩を塞げばよいので、直す場所が一意に決まる。

**歩行網スキャンでは絶対に見つからない。** あれは街路の上だけを歩く。
閉じ込められるのは、いつも街路の外(壁の厚みの中・汀の岩・防波堤の先)。

見つかった原因 —

* **`collide` と `groundAt` で「歩廊の上」の高さの窓が食い違っていた。**
  `collide` は歩廊から ±2.6m を「歩廊の上」とみなし、`groundAt` は 1.45m
  より高い床を「届かない」と捨てる。その 1.45〜2.6m の帯では、**壁体に
  弾かれもせず歩廊にも乗れない**。南の海壁でそこに入り込み、外は 5m の崖・
  内は登れない段、という袋小路になった(ユーザー報告)。
  **二つの判定が同じ物を測っているなら、閾値も同じでなければならない。**
* **押し出す向きを「中心線から見てどちら側か」で決めていた。** 石の厚みの
  中では中心線までの距離が 1m を切り、向きがほとんど乱数になる。海側へ
  弾き出されて崖の上に降ろされた。側は壁の輪と `OUTSIDE_WALKS` で決める。
  **迷ったら市内側。閉じ込めるより街へ戻すほうが常に正しい。**
* **海と汀へ落ちる縁が開いていた。** ポルポレラの先端(1.5m → −4.6m)、
  プロチェ橋の東の磯。床が水面下、または 1.2m より低い所へ 1.6m 以上落ちる
  なら、そこは縁。地形の勾配を登る向きへ、禁止域を出るまで押し返す。
  **見えない壁(collider without geometry)を足さずに済んだ** — 規則で
  塞げるなら、そのほうが良い。

計器自身の罠: **床は「押し返された先」で問う。** 要求した点で問うと、collide が
安全な所へ戻しているのに「危険な床に立てる」と数え、罠が 1 つ消えなかった。
また格子の一歩は実際の移動より粗いので、段差の上限をそのまま当てると坂が
「下れるが登れない」になる(2m 格子で 15 箇所の偽陽性)。勾配で許す。

実測 9 箇所 469 マス → **0**(格子 1.25m・到達 27,839 マス)。

### 描かれた床と当たり判定の床 — `tools/floortest.mjs`

`plan.groundAt` は足が乗る高さ、実三角形の最上面は目に見える高さ。
この二つがずれていると、人も player も石に埋まる/浮く。3,700 点で測って
部位ごとに束ねる。

    node tools/floortest.mjs [--all]

**`plan.groundAt(x, z)` は `curY` を渡さないと嘘をつく。** 層の解決は
「今の体の高さからの距離」で tier を決めるので、`curY` が `undefined` だと
全候補が tier 0 に落ち、`dy < best.dy` が NaN 比較で常に false になって
**最初の候補**(= 広場)が返る。これで「大聖堂前の石畳が 0.47m 高い」と
誤報し、無い欠陥を直しかけた。正しい問いは「**見えている床の上に立っている
体**に対して groundAt は何を返すか」。先に実三角形で床を取り、それを curY に渡す。

直した本物の欠陥 —

* **帯の高さを中心線の一点で決めていた。** 幅 6m の舗装リボンを中心線の高さで
  水平に張っていたので、傾いた通りでは描かれた石畳が当たり判定の面より最大
  0.47m 高くなった。**列ごとに測る**(刻みも 2.4m → 1.0m)。
* **Z ファイト避けの `lift` が、足が沈む量そのものだった**(0.014〜0.026m)。
  間隔は coplanar 検査の閾値 4mm より広ければよい。0.002 / 0.007 / 0.012 /
  0.017 に刻み直す(路地 / 街路 / 大通り / 門の敷居)。中央 +0.026 → +0.004。
* **門の敷居も `groundAt` を curY 無しで呼んでいた。** 歩廊デッキ(pri 6)を
  拾って敷居が 0.74m せり上がり、歩行網スキャンが「足の上に床がある」と鳴った。
  門の高さを渡し、さらに門の床から ±0.35m に抑える。

実測 食い違い 3,504 / 3,715 点 → 761(残りは意図的な 12〜17mm の間隔)。
足が床と合わない人 149 → 3。

**`box(w,h,d,x,y,z)` の `y` は底であって中心ではない。** 「中心 y=0 だから
足裏が 0.028m 下」と読み違えて足を持ち上げ、逆に 2.75cm 浮かせた。
**定義を読んでから直すこと。** 二つの計器(foottest と structure の接地)が
反対方向に動いたのがその合図だった。

### 足が床に埋まる — `tools/foottest.mjs`

人は 400 体近くいるので、一体でも埋まっていれば必ず誰かの視界に入る。
**腰ではなく足の裏で、実三角形の床に対して**測る。

    node tools/foottest.mjs [--all]

原因は三つ重なっていた(合計 0.13m。ユーザーに「足がめりこむ」と言われた量)。

1. **歩行の沈み込みが足まで下げていた**(0.071m)。脚を開くと剛体回転で足裏が
   浮くので骨盤を下げていたが、体ごと下げると **接地している側の足も沈む**。
   沈み込みを足首より上だけに効かせる(`smoothstep(0.02, 0.30, transformed.y)`)。
2. **足の箱の中心が y=0 だった**(0.028m)。インスタンス原点は「床に置く点」
   なのだから、足裏をそこに合わせる。箱の中心は 0.0275 へ。
3. **舗石は当たり判定の面より高く描かれている**(0.02〜0.08m)。これは残す —
   人を持ち上げて誤魔化すのではなく、**床の側の食い違いが直すべき欠陥**で、
   walkability が既に「描かれた床と体が立つ床が食い違う」と 43 点で鳴らしている。

実測 149 体 → 11 体(最悪 0.150m)。

**計器の罠が二つあった。** (a) `buildTriangles` の `owner` は物ではなく
**物の添字**。物として扱うと除外が効かず、自分の胸に当たって「404 体中
369 体が 1.2m 埋没」と出た。(b) 灯りの落とし影のような板の飾りを床に数えると
「灯りの下に立つ人は全員埋没」になる。床として数えないものを明示する。

**別の計器と数字が食い違ったら、どちらの基準が正しいかを言う。** 足を正しい
位置(足裏 = 原点)に直したら `structure` の接地は 206 → 237 に増えた。同じ人を
2.8cm 下からではなく足裏で測るようになっただけで、増えた分は舗石自身の
ばらつき(±0.04m)。**数字が悪くなったのは世界ではなく測り方が正直になったから。**

### 裏から見ると消える面 — `tools/culltest.mjs`

「板に見える」を目で探すのをやめるための計器。同じ視点を FrontSide と
DoubleSide で二回描き、ピクセルを突き合わせる。**違うピクセル = そこに面は
あるのに、こちらを向いている面が無い場所。** 塊に分けて重心へレイを飛ばし、
「どの作り方の面か」まで答える。

    node tools/culltest.mjs                       shots.txt の定点すべて
    node tools/culltest.mjs --png name:x:z:...    重ね絵も書く

**計器自身の罠**: `side` を変えると `shadowSide` の既定値も変わり、影の
落ち方まで変わる。それを差分に数えると「天井に帯がある」ような偽の指摘が
出た(ミンチェタで 11,302px)。影を明示して固定してから比べること。

これで見つかった一族 —

* **平行な二枚を「同じ巻き」で張る。** `quad` は巻きから法線を出すので、
  内側の一枚は法線が石の中を向いて消える。階段の手すり(空洞に見える)、
  螺旋の桁、家の軒の鼻隠しと軒天。**二枚組を張るときは必ず外向きを明示する。**
* **走査の向きが引数で入れ替わる所。** 塔の門口の袖壁は `side` で `c0→c1`
  の向きが逆になり、片側だけ法線が石の中を向いていた。**塔の中から見ると
  壁が透けて、向こうのアーチと海が見えていた**(実測 1 視点 66,075px)。
  外向きを渡していれば起きない。
* **半割の筒。** 棟瓦を `thetaLength = π` の樋で作っていた。底が無いので
  斜め上から覗くと中が見える。丸のまま棟に半分埋めるほうが安く確実。
* **上下が入れ替わる寸法。** 門口の塊の底を `deckY − 0.6` で固定していたが、
  敷居 `yFlG` は「門口の下を実際に通る歩廊の一番低い所 − 0.75」なので、
  斜路の途中に立つ塔では **底が敷居より上**に来る。見付が上下逆に張られ、
  下向きの板が通路の床の 0.45m 上に浮いた(実測 1 視点 194,217px = 画面の 12%)。
  **固定値と実測値を混ぜるときは、必ず大小関係を式で保証する。**
* **中身の無い階段。** 露天階段も螺旋も「両側の桁 + 下腹」で、天端が無かった。
  踏面は段ごとに離れた箱なので、段の隙間から梁の中が見える。さらに段は
  下腹の上面に載っていたので、下腹を正しく下向きに直した途端に
  「79 段が浮いている」と鳴った。**石の階段は中身が詰まっている** —
  踏面のすぐ下に斜めの天端を張る。接地 278 → 206。
* 螺旋の下腹は 0.50m しかなく、塔の中を斜めに横切る板だった。1.00m の斜梁に
  して、踏面の下に 0.10m 出の帯を回す。**縁が刃でなくなると板ではなくなる。**

### 計器が壊れているときの見分け方

メルロンの接地を測ったとき、最初「244 本すべて載っている」、次に「244 本
すべて浮いている」と出た。**極端に良い答えと極端に悪い答えが両方出たら、
壊れているのは計器のほう。** 前者は自分の底面を拾い、後者は始点を底の 2cm
下に置いて天端を見落としていた。座位の脚でも同じことが起きた(立っている
人にまで座位の足の位置を当てはめて 76/404 と出た。`aSit` で絞って 40/40)。

### 検査の側を直した例(理由を書く)

* 「胸壁が外側に無い」が 414 点で鳴っていた。外/内 を `(−tz, tx)` の符号で
  決めていたが、これはポリラインの巻き方向次第で反転する。→ 市の重心からの
  距離で決める。読んだ人間が毎回反対側を探しに行かないように。
* メルロンの接地を「底の隅から真下へレイ」で測ったとき、**自分自身の底面**を
  拾って「244 本すべて載っている」と出た。次にレイの始点を底の 2cm 下にしたら
  今度は「244 本すべて浮いている」と出た(塔の石は埋め込み 0 なので天端を
  見落とす)。正しくは「始点は底の 20cm 上・自分のメッシュは除外」。
  **計器が壊れているときは、極端に良い答えと極端に悪い答えの両方が出る。**
* 「面の巻きが裏返っている」を「同じ向きの稜線が 2 回」で数えていた。閉じた
  立体を二つ重ねると各稜線は正逆 2 回ずつ出る — これは重複であって裏返りでは
  ない。塔で 944 本の直しようのない指摘が出ていた。→ 正逆の数の不釣り合いで
  数え、境界稜線(既に「穴」として報告済み)は除く。実測 944 → 12。
